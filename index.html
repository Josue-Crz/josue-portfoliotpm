Mar-Apr 2026 / Open Source Maintenance

Turning a John the Ripper Good First Issue Into a Draft PR

I started with openwall/john issue #3896, a maintenance issue titled "Consistently (don't) split long source file lines." At first glance it looked like a formatting task. Once I read deeper, it became a lesson in how small style decisions can affect portability, readability, and contributor trust inside a mature C codebase.

What the issue was really about

The issue called out a long OpenBSD-SoftRAID test vector that had been split with backslash continuations. The maintainer proposed a safer approach: close the string on one line, reopen it on the next, and let the compiler concatenate adjacent string constants. That avoids depending on details like trailing whitespace. The second part of the issue was consistency: if one long source line is split, similarly long lines across the project should be handled with the same rule.

How I approached the draft PR

My first draft built on magnumripper's earlier PR #3908. I focused on src/openbsdsoftraid_variable_code.h, split long test vectors into adjacent string constants, and experimented with an .editorconfig line-length rule. I originally aimed for short 80-character splits around delimiter boundaries because that felt readable to me.

The maintainer feedback helped me recalibrate. The project did not want a broad delimiter-based refactor, and it did not want lines split that aggressively. The better target was closer to the existing project discussion: roughly 2000 characters per line for these huge vectors, with changes scoped to the original issue instead of expanding the problem.

Validation and takeaway

I tested the OpenBSD-SoftRAID format with ./john --test --format=openbsd-softraid, and the benchmark completed successfully. The bigger win was learning how to turn maintainer feedback into a better contribution: read the history, stay inside the issue's scope, preserve behavior, and ask clarifying questions early when style and maintainability are part of the bug.

  • Issue: long C/header source lines needed consistent treatment.
  • Draft PR: split OpenBSD-SoftRAID test vectors using adjacent string literals.
  • Lesson: in a mature security tool, "just formatting" still needs technical discipline.

Feb 2026 / Security & Full Stack

Hardening Keyshade.io Through Input Field Sanitation

Keyshade.io is an open-source secret and configuration management platform. Because it helps teams protect API keys, credentials, tokens, and deployment configuration, the inputs around projects, environments, variables, secrets, and users have to be handled carefully. Our CodeDay team worked on strengthening that front gate: the point where user-controlled text first enters the system.

The security problem

The issue was not encryption itself. It was the input path around the application. If unicode, emojis, script-like strings, or unexpected special characters are accepted too freely, they can create broken slugs, unsafe requests, confusing UI states, or validation gaps between frontend and backend behavior. These are the same kinds of trust-boundary weaknesses that make XSS and malformed-input bugs possible. In a secrets platform, even small validation mistakes deserve attention.

Where I investigated

I focused on the platform side first and looked for form entry points with searches around onSubmit and handleSubmit. That led to files such as auth-email-form.tsx, otp-input-form.tsx, and updateIntegrationSheet/index.tsx. I also traced helper-level validation through is-email-valid.ts, which helped connect individual forms to reusable validation logic.

The schema-driven solution

The team PR introduced centralized Zod schemas, including AlphaNumericStringSchema, VariableAlphaNumericStringSchema, ExtendedAlphaNumericStringSchema, and a color-code variant. Instead of writing one-off checks inside every component, the validation rules lived in the shared schema package and were applied across project, environment, integration, personal access token, secret, variable, user, workspace, and workspace-role request shapes.

On the frontend, the project creation flow used schema parsing before sending a request, showing a toast when a project name was not alphanumeric or was empty. The larger security idea was defense in depth: frontend validation improves feedback, while backend validation still needs to reject unsafe input because browser-side checks can be bypassed.

Collaboration and coordination

The work also had a product-management layer. A maintainer pointed out overlap with Keyshade issue #929, which described unicode values being accepted and then stripped into broken slugs. We clarified how our work related to the existing thread, asked where helper logic should live, and coordinated dependent frontend, backend, and CLI PRs so the shared schema changes could land cleanly.

  • Issue: user input needed stricter alphanumeric validation.
  • Solution: shared Zod schemas with safe parsing before data moved deeper into the app.
  • Lesson: security work is also coordination work when multiple contributors touch shared contracts.
